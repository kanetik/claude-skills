# Waiting for reviewer activity (SKILL.md step 3 detail)

**All of this concerns bots only.** The `skeptic` reviewer runs synchronously and its review is on the PR by the time it returns, so it is never pending, never polled, and never waited on. Where `reviewers` contains no bot, the loop has no wait step at all — step 2 comes back with the round's findings in hand and goes straight to step 4 — and the re-entrancy machinery below matters only in that a run can still be interrupted between rounds.

## Poll on a timer — no events reach a local terminal to wait on

A local terminal can't *receive* GitHub webhook/event deliveries, so the loop **drives its own wakes by polling**: schedule a self-wake on a fixed cadence and reconcile the PR on each tick. Polling is the mechanism here, not a fallback.

**What each poll must catch.** Reconciling the full PR state every tick covers every transition that ends a wait — including the quiet ones a reviewer never announces: a **clean/approving verdict** (an APPROVE, or a clean verdict in an issue comment), a **"no new comments" review** (e.g. Copilot's), **CI completion — success *and* failure** (`statusCheckRollup` going green or red), **new pushes**, and **merge-conflict transitions** (`mergeStateStatus` → `DIRTY`/`BEHIND`). These are the "reviewer went green, move on" signals; the poll catches every one within one cadence.

**Wake ladder — feature-detect, take the highest available:**

(a) **Self-scheduled wake** — a scheduling primitive (`/loop <cadence>`, `ScheduleWakeup`, `CronCreate`) that re-invokes you at the cadence carrying the continuation payload; reconcile on the tick. Preferred in a local terminal — cheapest and simplest.
(b) **Background polling monitor** — a *background* task that fingerprints the PR's head-commit/review/comment/CI/merge state and emits on change (snippet below). It runs in the background and the agent **ends its turn** — not a foreground `sleep` busy-wait. **Auto-wake is host-dependent:** this rung re-invokes you only where the host turns a background process's output into an agent wake. In a plain terminal that output is just a human-visible notification, not a self-resume — where that's all you get, the change is surfaced to the user and you treat it as rung (c). Use only when rung (a) is unavailable; (a)'s self-scheduled wake is the dependable local mechanism.
(c) **Single-pass hand-back** — do one reconciliation pass, then stop with "re-invoke `/pr-review-loop` to continue." Last resort, only when (a) and (b) are both unavailable.

Never **foreground**-busy-wait with `sleep` for reviewer activity — that blocks the turn instead of yielding. **Re-arm on every wake** (re-schedule / restart) until the PR is merged or closed; do it silently.

End the turn. On every wake, re-pull and reconcile (below), then act. Stay in the **120-240s band (2-4 minutes)**: frequent enough to react promptly, and ≤270s keeps each wake inside the 5-minute prompt-cache window (cheap); >300s incurs a full context replay per wake. The `/loop` idle default of 1200-1800s is far too slow for a review loop — set the cadence explicitly.

### Background fingerprint poll (ladder rung b)

An illustrative starting point — adapt it. Hash the PR state, and emit when the hash changes; run it in the background (whether that emit auto-wakes you or only notifies a human is the host-dependent question rung (b) covers).

```bash
fp() {
  gh pr view <num> --repo <owner>/<repo> \
    --json headRefOid,reviews,comments,statusCheckRollup,mergeStateStatus \
    --jq '[.headRefOid, (.reviews//[]|sort), (.comments//[]|sort),
           (.statusCheckRollup//[]|sort), .mergeStateStatus]' | sha256sum | cut -d' ' -f1
}
prev="<baseline>"                  # the fingerprint from your last reconciliation
while :; do
  sleep <cadence>
  cur=$(fp); [ "$cur" != "$prev" ] && { echo "pr <num> changed"; prev=$cur; }
done
```

When you adapt it: keep `headRefOid` so pushes register even in a repo with no CI; `sort` each array so result-ordering noise (and either CI shape — CheckRun or legacy commit status) doesn't fake a change; seed `<baseline>` from the fingerprint you took at your last reconciliation (and `sleep` before the first check) so a re-arm doesn't immediately re-emit; add a periodic floor emit if you also want a liveness signal. **Gotcha:** when the git remote is a proxy or other unrecognized host, bare `gh pr view` fails with *"none of the git remotes ... point to a known GitHub host"* — pass `--repo <owner>/<repo>`, and use explicit owner/repo/number on `gh api graphql` (the convention `reference/mechanics.md` already uses).

## Re-entrancy — build for it

Under polling the loop is **re-entered across wakes**, not run as one process. Make each wake idempotent:

1. Re-pull (`git fetch && git pull --ff-only`).
2. Re-derive where you are from the PR (SKILL.md step 1 gathering): unresolved threads, review states with their `commit_id`s, bot issue comments, skeptic's coverage record, the current HEAD sha (and the latest push timestamp, for the sha-less fallback), tracked-bots set — **read all three surfaces against current HEAD** (SKILL.md "Reading reviewer state") before concluding any bot is still pending. The HEAD sha is the one that matters: staleness is "did this reviewer see this code", which a sha answers and a clock only approximates.
3. Act (evaluate / request / wait).
4. Re-schedule the poll, then yield.

**Resume at step 3, not the top.** A wake re-enters the wait/evaluate cycle — it does NOT re-run the first-run preamble (arg parse, modifier/override detection); that was kickoff work, and redoing it wastes effort and can re-prompt the user. The catch: anything the preamble *decided*, or run-scoped state the PR doesn't record, must instead ride in the **wake payload** (next section). Never hold loop-critical state only in turn-local memory — a wake may be a fresh context.

## Carried state — what the PR can't tell you

Most state re-derives from the PR. Six pieces don't, and must be carried in the wake/continuation payload (in the common single-context run this is just in-memory and always available):

- **Iteration counter** (drives `max_iterations`, SKILL.md step 9). Nothing on the PR records "how many times has this loop run." Carry "iteration N of max M" in the continuation. **Time-based tier:** schedule the wake with a continuation prompt — e.g. `"Resume the PR-review-loop at step 3; iteration N of max M; active modifiers: cap disabled, only copilot; dropped happy: copilot; excused: codex."` Do **not** schedule a bare `/pr-review-loop` re-invocation — that restarts the preamble and loses the count (reserve `/pr-review-loop` for kickoff and for the single-pass manual hand-back).
  - **Fallback when a context-less wake carries no counter:** scan the PR's commits for the `PR-Review-Loop: <N>` trailer (SKILL.md step 6), take the highest `<N>`, and resume at **`<N>+1`** (iteration `<N>`'s commit is already on the PR). The `commits` connection returns full messages, so this is a direct read. It's a *floor* — iterations that committed nothing carry no trailer, so it may under-count, the safe direction for a cap.
- **Dropped-happy set** (SKILL.md step 4). A dropped bot's clean verdict still sits on the PR and the tracked set still counts it, so re-deriving from PR history alone would re-add and re-request it — the resurrection stickiness forbids. Carry the set, e.g. `"...; dropped happy: copilot, codex."` **No carried set? Do NOT infer drops from stale clean verdicts** — a stale-clean bot may simply have gone clean on an earlier commit and still need the new HEAD, which step 4 says to re-request. Re-derive conservatively (re-request the stale-clean bot — one extra review is harmless; silently dropping a bot that may have concerns is not). **This is a deliberate exception to step 4's stickiness, not something step 4 authorizes** — under this skill's rules a bot is dropped the moment it goes clean, so "stale-clean" and "dropped-happy" name the same bot and the fallback necessarily re-requests one that stickiness would not. It is the right trade only because the alternative is dropping a reviewer that might still have concerns; where you want stickiness to survive a context-less wake, use the durable marker below rather than this fallback. For full stickiness across context-less wakes, record each drop **durably at drop time** in a marker you own and read back (e.g. a hidden `<!-- pr-review-loop: dropped-happy: … @ <sha> -->` line in the PR body). Skeptic is never in this set — it never drops (step 4), so a wake needs to carry nothing about it.
- **Excused set** (SKILL.md step 4). Run-scoped, nowhere on the PR, and load-bearing twice over: it is subtracted from the external-push engage set, and `accountable = reviewers − excused` is what convergence is judged over. Lose it and the excused reviewer re-enters `active` — re-engaged, waited on for the full timeout, the same question put to the user again — *and* rejoins the accountable set, where a reviewer that could not run must now be happy for the invariant to hold. It never can, so the run burns to the cap and reports "did not converge" with every real finding settled. Unlike dropped-happy, **it does not reset on an external push**.
- **Effective invocation modifiers** (a disabled cap, a narrowed reviewer set). Not PR-derivable; carry them so a context-less wake doesn't silently revert to defaults.
- **Repair lineage** — for each fix round, which finding it was answering. This is what the revert lever and the cap report's "longest live repair chain" are computed from (SKILL.md steps 5 and 9), and it is the one number in that report that is **cheap and exact only while carried**. It is not strictly underivable — step 5's own provenance lookup (blame the line, read the trailer on the introducing commit) applied across the PR's historical threads and their disposition replies reconstructs the chain approximately — but that is many lookups over the whole history to recover something a single carried string holds precisely. Carry it compactly — e.g. `"chains: thread#7 -> r3 -> r5 (depth 2)"`. **Where a context-less wake carries none, either reconstruct it from blame if the run warrants the cost, or say the chain depth is unknown — never report a number you did not establish.** There is no safe floor here: an absent lineage looks exactly like depth 1, which reads as "this run is healthy, continue" — the opposite of what a run deep enough to reach the cap needs the user to hear. The other three cap-report numbers (rounds since the last blocking finding, share of findings in loop-written code, diff growth) are all PR- or git-derivable and survive a fresh context intact.

- **Whether this run has already spent its one whole-change ask** (SKILL.md step 4's convergence clause). That clause asks skeptic to re-read at an unmoved HEAD exactly once, and "once" is the only thing bounding step 2's skip exception. A *failed* ask leaves no trace to re-derive it from: a skeptic run where no unit returned blocks posts nothing at all, so the PR after it is byte-identical to the PR before, and a re-entered wake would ask again. Carry it, e.g. `"...; whole-change ask: spent @ <sha>."` Scope it to the HEAD sha it was spent at — a later push is a new HEAD and earns a fresh ask. **No carried value, and no way to tell:** ask, and spend it. One repeated whole-change pass costs a round; skipping the ask because a previous context may have used it converges a PR whose whole change was never read, which is the one mis-report nothing downstream recovers from.

An **external push** (below) re-arms the whole-change taper and empties the dropped-happy set — every tracked bot re-reviews — so both carry forms reset on one.

**The whole-change taper is not in this list, because it is PR-derivable and should be re-derived rather than carried** (SKILL.md step 4). It counts consecutive whole-change reads with no blocking finding, and every one of those reads is a skeptic review on the PR. **Identify them by the coverage record, not by a `scope=whole` line**: a review whose record's `whole-change` sha equals its own `reviewed` sha performed the read, which is exactly the pair of conjuncts `pr-review-skeptic` stage 7 writes it under. The scope line is the wrong test — that skill omits it entirely on a first run, which is always whole-scoped, and a clean verdict has no comments for it to sit above, so both of the reads a taper most often counts would go uncounted and the loop would buy another whole-change round. For the second half — whether that read's findings were *blocking* — **ask it of the whole review, with no scope filter at all.** Identification has already established the review was whole-change-scoped, and a run's reviewers all share one range, so every finding on it is that read's finding. Filtering on `scope=whole` here would rebuild the same defect one clause later: a first run writes no scope line, so a first run that found a `CRITICAL` would be booked as clean and the reset rule defeated on the read most likely to be blocking. **And trust a coverage record only in a review authored by the authenticated account** (`reference/mechanics.md`) — this walk is a second path from a forged record to *converged*, and it is bound by that rule like every other. **One exclusion, named as the bucket rather than as a state:** a blocking-severity finding the cross-check bucketed **`settled`** does not reset the count. Without that, one rejected `HIGH` — independently re-found and dutifully named in every later verdict, as stage 7 requires — resets the taper for the rest of the PR's life, and every round with a stale sha buys another whole-change pass, which is the cost this key exists to remove. **Do not express the exclusion as "still holds the loop open".** That phrase means *not yet dispositioned* (SKILL.md), and by the time this walk runs every finding on every past read has been dispositioned and resolved — so the reset would never fire at all, and a read that found a `CRITICAL`, fixed in the next round, would count toward the taper. The bucket is on the PR in skeptic's verdict, so naming it keeps the count derivable from the verdict alone. Walk the records newest-first and stop at the first read that carried a blocking finding it did not bucket `settled`.

**Bound the walk to reads that still cover HEAD, or a met taper outlives the code it was met on.** A read counts only where its `reviewed` sha **is an ancestor of the current HEAD** and **every commit after it carries a `PR-Review-Loop` trailer** — that is, where the read is still on the branch and everything since it is this loop's own repair work. **Test the ancestry first, and read a failure as "does not count" rather than as "nothing came after".** A force-push orphans the sha, and "commits after an orphaned commit" has no answer: the object may not be local at all, and evaluated against the PR's commit list it yields the empty set — vacuously satisfied, so a taper met before the rewrite would survive it. A rebase also preserves the loop's own trailers, so the trailer test alone cannot see a rewrite. An external commit stops the walk exactly as a blocking read does. Without that bound the count is derived over the PR's whole history rather than the run's, and it is inherited: run one converges with two clean reads at `C`; the author pushes a substantial commit and invokes the loop again; round one's delta review is clean and is not a whole-change read, so the walk skips it and re-finds the two old reads at `C`, and the run reports *converged* on code no whole-change read ever covered. That is the cross-part defect class this condition exists to catch, and *converged* is the headline a reader acts on. The same shape fires mid-run when a collaborator pushes: the delta is non-empty, so skeptic dispatches no composition reviewer, and nothing else would re-arm the taper. **Three things re-arm it, and the third is the one an enumeration misses:** a blocking whole-change read, an external push, and **a rewrite of history**. **What does *not* re-arm it is the loop's own repair, however much of it there is — and that is the cost this key buys, so say it rather than calling the gap small.** Once met, the taper holds across every later fix round, including rounds that fix blocking findings. Each of those rounds gets its own delta review before anything converges, and none of them gets a fresh cold read of the whole change. So a long repair tail can sit behind a met taper unread as one thing, which is the composition-defect class the whole-change read exists for. **The disclosure is the mitigation**: the converged summary names the sha the whole change was last read at, and a reader who sees it several rounds back knows what they are merging. A re-arm on blocking fixes was tried and withdrawn as underivable: `disposition=fixed` carries no commit, *already-fixed* stamps the same marker while moving no code, and ordering a thread against a read would need either the repair lineage — carried state, which the taper deliberately is not, since it is re-derived from the PR — or a clock, which this skill rejects as a staleness test everywhere else. A rebase or force-push is not an *external push* by this skill's own definition — that test is commits lacking the `PR-Review-Loop` trailer, and a rewrite preserves the loop's own trailers — but it orphans the sha the read was anchored to, so the ancestry half is what catches it. Do not restate the reset set as a two-item list anywhere; state the two conditions a read must meet and let the events fall out. **On the external-push half it re-arms exactly as it resets the dropped-happy set** — one paragraph of this section already treats an external push as the event that invalidates a verdict, and this is the same event invalidating the same kind of claim. A carried number would be a second copy of something the PR already answers exactly, and the failure modes are asymmetric: a lost count re-reads the whole change once more, which is the cost the taper is trading against, while a *wrong* carried count converges a PR on a cold read that never happened.

**The rest of skeptic's state is PR-derivable**, which is what makes a context-less wake cheap now that it posts. Its review carries the `<!-- pr-review-skeptic -->` marker **and a coverage record naming the sha its reviewers read**; its findings are threads with the same marker; your dispositions are replies on those threads and the resolution state of each. A wake reads all of it back and knows exactly where the round stands, and the coverage record means it knows that without needing a push event or a clock. Two things follow: the step-2 skip check ("a marker-carrying review whose record names the current HEAD sha") is what stops a re-entered wake dispatching a second eight-reviewer pass over a commit already reviewed, and where no such review exists, re-running it is correct rather than wasteful.

**The one exception is the whole-change ask above**, and it is why that bullet exists. Step 4's clause fires precisely when the record *does* name current HEAD, so the skip check would otherwise block it and step 2 carves it out — which means this one dispatch is not prevented by the sentence above, and nothing on the PR records that it happened when it failed.

## Lockstep across the round's engaged bots

Wait until every bot **engaged for the current commit** has either delivered a verdict (a formal review OR an issue comment, clean or findings), been dropped as happy, or been **excused for the run** (all three: step 4). The engaged set is `active ∩ reviewers` for a normal round, and **`(tracked − excused) ∩ reviewers`** after an external push — previously-happy configured reviewers come back; excused and uninvited ones never do.

Excused is the exit that is easy to omit, and omitting it hangs the loop: the excusal is offered from inside this very step (the timeout, below), so a condition listing only "delivered or happy" is still unmet the moment the user grants it — the poll re-arms and the wait never ends, never reaching the step-4 handling that was supposed to unblock it. **Recompute the engaged set from `active` when a reviewer is excused, and let control pass to step 4 immediately.** "Engaged for the current commit" is a historical fact that the excusal does not undo, so it cannot be the thing you test. Convergence is gauged on `reviewers`; a reviewer that turned up on its own is triaged but never blocks the loop.

**Skeptic is never waited on.** It isn't requested, so nothing is pending; it runs synchronously and its review is already posted before the round's wait would begin. Where `reviewers` mixes both kinds, run skeptic first and let its findings join the same batch as the bot's — one combined evaluation per round, for the reason below. A list with no bot in it has no wait at all, and a wait armed for one would never end.

**Batch-evaluate the round's combined feedback in one pass** — don't react to bot A, push a fix, then let bot B review the new state. That compounds iterations and misses contradictions (one says X, another ¬X) and overlap you'd catch seeing both side by side.

**Newly appearing reviewers count.** One that posts a review — or a review-style verdict comment (not CI/noise) — during the wait joins the tracked set immediately and is batched into this round's lockstep. It is not in `reviewers` unless configured, so step 8 won't re-engage it and it doesn't gate convergence; its findings are still triaged in step 5, and still get dispositions and resolved threads like any other. This is also the path a review the **user** posted by running `/pr-review-skeptic` themselves arrives on: it carries the marker, so read it as a skeptic verdict for the current HEAD and fold it into the round rather than re-running the reviewer over the same commit.

## External pushes during the wait

If `git pull` on wake brings in commits the loop didn't author (a teammate or automation), pending reviews are stale against the new HEAD — and this is the one case that **re-engages already-happy bots**. External code is code no reviewer has seen, which no prior clean verdict can cover. Return to step 1 and rebuild the active set from the tracked set, re-engaging **`(tracked − excused) ∩ reviewers`**: every configured reviewer, previously-dropped-happy ones included, re-reviews the new HEAD (an uninvited reviewer is still never re-engaged, and neither is an excused one — see below) (step 2's per-reviewer "has it covered the current commit?" check re-triggers each). An external push is one whose new commits **lack the `PR-Review-Loop` trailer** step 6 stamps — the PR-derivable signal that separates the loop's own commits from everyone else's, so even a context-less wake can tell them apart. (A user manually re-requesting one happy bot is the other, narrower re-engagement path — step 4.) Skeptic needs no special handling here: it re-runs on every push regardless, so an external one is just another push to it.

## Timeout for unresponsive bots

If a bot doesn't respond within ~20 minutes of being triggered (or ~20 min after the push that should have auto-triggered it), surface to the user — don't silently hang. **Before declaring it unresponsive, reconcile all three surfaces against HEAD** — its verdict may have arrived as an issue comment a prior poll didn't catch, in which case it's done. The user decides: skip it, wait longer, or terminate.

"Skip it" means **excused for the run**, not for this iteration (SKILL.md step 4). A bot skipped for one iteration is re-requested by the next step 8, stalls the next wait for another twenty minutes, and asks the user the same question again — ten times over, on a broken integration, before the cap report finally arrives. And because nothing removed it from `active ∩ reviewers`, the loop cannot terminate anyway: the run ends as *did not converge* even where every real finding was settled. So drop it from `active`, end this wait, don't re-engage it, and name it in the summary as excused and unreviewed. Carry the excused set in the wake payload, and **do not reset it on an external push** — unlike a stale happy verdict, a reviewer that could not run is not made able to run by new code, so resetting it just charges the user another twenty-minute stall and the same question.

**Where it is the last reviewer**, excusing it means nothing reviewed this HEAD, so the run cannot report convergence (SKILL.md step 4's invariant). Say so as part of the offer.

## Optional self-review — push BEFORE triggering, not during the wait

Discretionary: if you spot something bots will surely flag (typo, clear bug, lint-level issue), fix and push it *before* requesting reviewers so they review the cleaner version. Don't push during an active lockstep wait — that means bots review different states. Hold mid-wait findings for the step-5 batch.
